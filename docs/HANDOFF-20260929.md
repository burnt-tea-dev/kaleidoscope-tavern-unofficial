Everything in this note is reproducible from this repository alone. No world save, server

## Correction after tracing the actual event consumers

The historical `used=aim` rows below are **not proof that aim reached slot selection**.
At `8add56c2`, `storageHit()` logged them and then dereferenced `hit.face`. Ordinary touch
intentionally had no `hit`; the resulting exception silently returned the mirrored event
point. This has been reproduced through the production preflight AND deferred interaction:
`aimed=(1,.74,.12)` but both consumers received `(0,.84,.88)` and selected slot 0, not 2.
A second defect kept inset selection boxes unrotated after facing permutations.

See [STORAGE-AIM-ROOT-CAUSE-20260929.md](STORAGE-AIM-ROOT-CAUSE-20260929.md) for the two
repairs and same-tests old/partial/fixed counterexamples. New storage logs use `schema:2`
and `resolved` for the value actually returned. Only this new schema may be used with the
pick-versus-display discriminator below. Native touch-client acceptance remains pending;
production-adapter tests are not client rendering tests.

## The open report

> All east/west-facing racks are uniformly left-right flipped.

Reproduction is on a live Bedrock server; the pick path is server-side script, so a script
change needs a stop/start (a `reload` cannot see newly added files and leaves components
unregistered).

## What is already established (do not re-derive)

1. **The engine reports interaction hits in the clicked face's own basis.** Measured from
   live diagnostic pairs (`[Tavern storage hit]`, event vs raycast for the same click):
   north/south faces are world-true, east/west raycasts arrive z-mirrored, the hanging
   rack's bottom face reports the event 180°-rotated and the raycast x-mirrored. Encoded
   as data in `runtime/BP/scripts/core/hit-basis.js` (`HIT_FACE_BASIS`, `worldFromHit`).
2. **Slot addressing through the display map** for the hanging glassware
   (`glasswareHolderStateSlot`): east/west facings render each stored glass in the
   diagonal world quadrant. If a future release makes slots world-fixed by swapping the
   facing-1/facing-3 `bone_visibility` expressions in `blocks/glassware_holder.json`,
   that compensation must be removed in the same change.
3. **Aim-ray picking** (`runtime/BP/scripts/core/aim-hit.js`): the player's own eye ray
   intersected with the block's selection box, used for **every input mode** since
   `e5dca5f3`. Box origins are x/z centre-relative and y bottom-relative; the box table is
   asserted against the shipped block definitions by `tools/glassware/aim-hit.test.mjs`.
   Per-mode engine values remain only as the fallback when the ray misses.

## Capture these rows first

`[Tavern storage aim]` fires for the first 12 storage picks per session and records
`mode`, the engine event hit, the raycast hit, the aim point, the measured-basis result and
which source was used. `[Tavern glassware hit]` does the same for the holder. They are the
fastest discriminator:

- aim point correct + slot still wrong → the **display** is mirrored relative to the pose
  functions (compare `cellarCabinetVisualPose` / `tiltedRackVisualPose` /
  `circularRackVisualPose` against where the visual entity actually lands).
- aim point itself on the wrong side → the **pick** is still reading a mirrored value
  (check `used` in the row and add the face basis if the engine value was used).

## Constraint checklist for any deploy or release

- A version bump must update both manifests, the startup diagnostic, the guide payload
  version and `.github/release-request.json`, and every dependent pack's pin must be
  synced in the same change — otherwise startup validation refuses to run.
- Any file-level deploy must preserve local-only pack edits (private dependency UUID
  remapping, fence-connection block components). Compare content with those stripped.
- Added script files require a real restart, not a script reload.
- Never commit world saves, backups, server paths or pack content that is not intended to
  be public.

## Live evidence for the open report (2026-09-29, after `e5dca5f3`)

Twelve historical rows from a touch client, all **logged** `used=aim`. The correction
above establishes that these schema-1 rows could still return raw event coordinates
after logging; do not treat them as evidence of the final consumed point:

| block | face | engine event hit | aim point |
| --- | --- | --- | --- |
| `oak_cellar_cabinet` | East | (0.94, 0.90, 0.80) | (1.00, 0.83, 0.22) |
| `cellar_cabinet` | East | (0.00, 0.84, 0.88) | (1.00, 0.74, 0.12) |
| `cherry_cellar_cabinet` | North | (0.86, 0.85, 0.94) | (0.86, 0.78, 0.00) |

Two things worth keeping:

- The engine's event hit is z-mirrored on the first block but **180°-rotated** (x and z
  both flipped) on the second — the same shape class reported two different bases, which
  is why every per-face table was doomed and the aim ray is now the primary source.
- The calculated aim points (not necessarily the consumed points in those old rows)
  are consistent with the display poses: `cellarCabinetVisualPose(2,1)`
  renders slot 2 at z = 0.175 and the aim z = 0.16 picks that column.

If a left-right mirror is still reported, first require `[Tavern storage aim]`
`schema:2`, and compare `resolved` (not just `aimed` or `used`) with the pose and actual
slot/object. Keep the new `reason` when a fallback was used. Capture real touch hardware
results before deciding whether native rendering also needs repair.
