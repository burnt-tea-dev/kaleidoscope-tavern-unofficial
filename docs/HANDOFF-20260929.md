# Handoff — hanging glassware / cabinet slot picking (2026-09-29)

## Fourth correction — hanging glassware world-slot baseline (2026-09-29)

The later real-client report confirmed that the X-shaped pick/render relationship returned
after the cabinet/rack aim repair. This is a separate path: the hanging holder does not use
the stateful-storage event route. The third-round repair deliberately left a client-facing
mapping mismatch in the RP and compensated in BP with a facing-dependent state-slot remap.

That workaround is now retired. Java stores and renders holder slot N in world X/Z quadrant N
regardless of FACING. Bedrock now uses the same invariant: BP state IDs are always the Java
world quadrant; RP bone_visibility alone counter-rotates model bones so state N appears in
world quadrant N. The facing-1/facing-3 RP clauses and the BP remap must change together.

The previous regression proof had a blind spot: one test hard-coded the same diagonal display
formula it was meant to verify, while the asset checker used the rotation sign inferred before
the direct east/west client report. The checker now reads the shipped block JSON and geometry
using the measured client convention, and CI runs the actual furniture event route for all
four facings and Touch/KeyboardAndMouse/Gamepad.

This repair changes the RP. A server-only script replacement is not a valid acceptance test;
a real phone/tablet must receive the updated resource pack before judging the result.

Everything in this note is reproducible from this repository alone. No world save, server
path, credential or private pack content is included, and none may be committed.

## Correction after tracing the actual event consumers

The historical `used=aim` rows below are **not proof that aim reached slot selection**.
At `8add56c2`, `storageHit()` logged them and then dereferenced `hit.face`. Ordinary touch
intentionally had no `hit`; the resulting exception silently returned the mirrored event
point. This has been reproduced through the production preflight AND deferred interaction:
`aimed=(1,.74,.12)` but both consumers received `(0,.84,.88)` and selected slot 0, not 2.
A second defect kept inset selection boxes unrotated after facing permutations.

See [STORAGE-AIM-ROOT-CAUSE-20260929.md](STORAGE-AIM-ROOT-CAUSE-20260929.md) for the two
repairs and same-tests old/partial/fixed counterexamples. New storage logs use `schema:2`
and `resolved` for the value actually returned. Only this new schema may be used with the
pick-versus-display discriminator below. Native touch-client acceptance remains pending;
production-adapter tests are not client rendering tests.

## What is already established (do not re-derive)

1. **The engine does not supply one universal world-coordinate basis.** Historical live
   pairs showed north/south world-true, east/west raycasts z-mirrored, and hanging-rack
   bottom events 180-degree rotated with x-mirrored raycasts. The captured cabinet rows
   below additionally show different bases for the same shape family. Keep the existing
   `HIT_FACE_BASIS` only as a limited fallback; do not add another per-face table fix.
2. **Slot addressing through the display map** for the hanging glassware
   (`glasswareHolderStateSlot`): east/west facings render each stored glass in the
   diagonal world quadrant. If a future release makes slots world-fixed by swapping the
   facing-1/facing-3 `bone_visibility` expressions in `blocks/glassware_holder.json`,
   that compensation must be removed in the same change.
3. **Aim-ray picking** (`runtime/BP/scripts/core/aim-hit.js`): the player's own eye ray
   intersects the block's selection box. `e5dca5f3` intended to use it for every input
   mode, but the later return exception defeated that intention on ordinary touch.
   The present repair preserves the computed point and rotates non-square selection
   boxes with the shipped facing permutation. Box and permutation agreement is tested
   in `tools/glassware/aim-hit.test.mjs`; actual consumers are tested separately.

## Capture these rows first — schema 2 only

`[Tavern storage aim]` now records `schema:2`, `route`, `mode`, `facing`, engine event hit,
optional native ray hit, `aimed`, `used`, `resolved` and a fallback `reason`. `resolved` is
the point returned to preflight and captured for the deferred interaction. Diagnostic
failure cannot change it. The first twelve picks per script instance are logged; a player
with tag `kaleidoscope_tavern:debug_storage_aim` continues logging until that tag is removed.
The separate `[Tavern glassware hit]` log has not been upgraded to this storage schema.

- First verify `resolved` and the actual selected slot/object. If the input to selection
  is wrong or a fallback is used, investigate the pick path and recorded `reason`.
- Only when selection uses the intended point and the pose for that selected slot is
  correct, but the client shows the object elsewhere, investigate the display entity's
  real location/rotation and native rendering. Compare `cellarCabinetVisualPose`,
  `tiltedRackVisualPose` and `circularRackVisualPose` without reversing saved slot IDs.
- Never use old `used=aim` alone to exclude the pick path. A touch off-crosshair tap and
  the server eye ray may still express different intent; real touch testing remains required.

## Constraint checklist for any deploy or release

- A version bump must update both manifests, the startup diagnostic, the guide payload
  version and `.github/release-request.json`, and every dependent pack's pin must be
  synced in the same change — otherwise startup validation refuses to run.
- Any file-level deploy must preserve local-only pack edits (private dependency UUID
  remapping, fence-connection block components). Compare content with those stripped.
- Added script files require a real restart, not a script reload.
- Never commit world saves, backups, server paths or pack content that is not intended to
  be public.

Two things worth keeping:

- The engine's event hit is z-mirrored on the first block but **180-degree rotated**
  (x and z both flipped) on the second. This is why another per-face lookup cannot solve
  the whole report. The fix must preserve the independently computed point through return.
- The calculated aim points (not necessarily the consumed points in those old rows)
  are consistent with the display poses: `cellarCabinetVisualPose(2,1)`
  renders slot 2 at z = 0.175 and the aim z = 0.16 picks that column.

If a left-right mirror is still reported, first require `[Tavern storage aim]`
`schema:2`, and compare `resolved` (not just `aimed` or `used`) with the pose and actual
slot/object. Keep the new `reason` when a fallback was used. Capture real touch hardware
results before deciding whether native rendering also needs repair.
